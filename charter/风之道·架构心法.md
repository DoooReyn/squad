# 风之道·架构心法

> *"武学之道，不在于招式繁复，而在于心法通透。心法者，以简驭繁之术也。"*
> —— 吟游诗人 小柯

> 本心法是冒险团框架设计的指导思想，所有架构决策应以此为依归。

---

## 核心心法

> *"最好的架构是刚刚好满足需求的架构，不多一分，不少一毫。"*

1. **简洁胜于复杂** — 简单的代码更容易理解、维护和扩展
2. **变化是永恒的** — 代码必须易于适应变化
3. **重复是敌人** — 每一处知识都应该有单一、明确的表示
4. **不过度设计** — 只为当下需求设计，不为未来猜测
5. **各司其职** — 每个模块都应该有清晰的职责边界

## SOLID 原则

> *"面向对象设计的五大基石，掌握它们，你的代码将如诗般优雅。"*

### S — 单一职责原则 (Single Responsibility Principle)

**一个类或模块应该只有一个引起它变化的原因。**

```typescript
// ✅ 好的：职责分离
class Hero {
  // 只负责英雄的属性和行为
  public hp: number = 100;
  public attack(): void {}
}

class HeroView {
  // 只负责英雄的显示
  public updateSprite(hero: Hero): void {}
}

class HeroData {
  // 只负责英雄数据的存取
  public save(hero: Hero): void {}
}

// ❌ 坏的：职责混杂
class Hero {
  public hp: number = 100;
  public attack(): void {}
  public updateSprite(): void {}  // 视图职责
  public saveToDatabase(): void {} // 数据职责
}
```

**要点：**
- 一个类只做一件事
- 如果你想不出一个简洁的类名，说明它做了太多事
- Cocos Creator 中的组件天然符合单一职责

---

### O — 开闭原则 (Open-Closed Principle)

**软件实体应该对扩展开放，对修改关闭。**

```typescript
// ✅ 好的：通过策略模式扩展
interface AttackStrategy {
  attack(target: Node): void;
}

class MeleeAttack implements AttackStrategy {
  attack(target: Node): void {
    console.log('近战攻击');
  }
}

class RangedAttack implements AttackStrategy {
  attack(target: Node): void {
    console.log('远程攻击');
  }
}

class Hero {
  private attackStrategy: AttackStrategy;

  public setAttackStrategy(strategy: AttackStrategy): void {
    this.attackStrategy = strategy;
  }

  public attack(): void {
    this.attackStrategy.attack(this.node);
  }
}

// ❌ 坏的：每次添加新攻击方式都要修改 Hero 类
class Hero {
  public attack(type: string): void {
    if (type === 'melee') {
      // 近战逻辑
    } else if (type === 'ranged') {
      // 远程逻辑
    }
    // 添加新类型需要修改这里
  }
}
```

**要点：**
- 通过接口和抽象类隔离变化
- 使用策略模式、模板方法模式
- Cocos 的组件系统本身就是开闭原则的体现

### L — 里氏替换原则 (Liskov Substitution Principle)

**子类应该能够替换父类而不破坏程序的正确性。**

```typescript
// ✅ 好的：子类完全遵循父类契约
abstract class Enemy {
  abstract attack(): void;
}

class Goblin extends Enemy {
  attack(): void {
    console.log('哥布林攻击');
  }
}

// 任何使用 Enemy 的地方都可以用 Goblin 替换
function makeEnemyAttack(enemy: Enemy): void {
  enemy.attack(); // 无论是 Goblin 还是其他 Enemy 都能正常工作
}

// ❌ 坏的：子类破坏了父类的契约
class DummyEnemy extends Enemy {
  attack(): void {
    // 什么都不做，破坏了父类的预期行为
  }
}
```

**要点：**
- 子类不能削弱父类的方法功能
- 子类不能抛出父类没有预期的异常
- Cocos 组件继承时要注意保持行为一致性

---

### I — 接口隔离原则 (Interface Segregation Principle)

**客户端不应该依赖它不需要的接口。**

```typescript
// ✅ 好的：接口细粒度分离
interface Movable {
  move(x: number, y: number): void;
}

interface Attackable {
  attack(): void;
}

interface Healable {
  heal(value: number): void;
}

// 只实现需要的功能
class Wall implements Movable {
  move(x: number, y: number): void {}
}

class Hero implements Movable, Attackable, Healable {
  move(x: number, y: number): void {}
  attack(): void {}
  heal(value: number): void {}
}

// ❌ 坏的：臃肿的接口
interface GameEntity {
  move(x: number, y: number): void;
  attack(): void;
  heal(value: number): void;
  fly(): void;
  swim(): void;
}

// 墙不需要攻击和治愈，但被迫实现这些方法
class Wall implements GameEntity {
  move() {}
  attack() {} // 空实现
  heal() {}  // 空实现
  fly() {}   // 空实现
  swim() {}  // 空实现
}
```

**要点：**
- 接口应该小而专注
- 不要强迫类实现不需要的方法
- TypeScript 的类型系统让接口隔离更容易实现

---

### D — 依赖倒置原则 (Dependency Inversion Principle)

**高层模块不应该依赖低层模块，两者都应该依赖抽象。**

```typescript
// ✅ 好的：依赖抽象
interface ILogger {
  log(message: string): void;
}

class ConsoleLogger implements ILogger {
  log(message: string): void {
    console.log(message);
  }
}

class GameService {
  private logger: ILogger;

  constructor(logger: ILogger) {
    this.logger = logger;
  }

  public doSomething(): void {
    this.logger.log('Something happened');
  }
}

// ❌ 坏的：依赖具体实现
class GameService {
  private logger: ConsoleLogger; // 依赖具体类

  constructor() {
    this.logger = new ConsoleLogger();
  }
}
```

**要点：**
- 依赖接口而非实现
- Cocos 的 `@property` 装饰器本质上就是依赖注入

## DRY — 不要重复自己

> *"每一处知识都应该有单一、明确的表示。如果你发现自己在复制粘贴，那就是设计问题的信号。"*

```typescript
// ❌ 坏的：重复的代码
function getHeroHP(hero: Node): number {
  const component = hero.getComponent(Hero);
  return component ? component.hp : 0;
}

function getEnemyHP(enemy: Node): number {
  const component = enemy.getComponent(Enemy);
  return component ? component.hp : 0;
}

// ✅ 好的：提取通用逻辑
function getComponentHP<T extends { hp: number }>(
  node: Node,
  componentClass: Constructor<T>,
): number {
  const component = node.getComponent(componentClass);
  return component ? component.hp : 0;
}

// 使用
const heroHP = getComponentHP(heroNode, Hero);
const enemyHP = getComponentHP(enemyNode, Enemy);
```

**要点：**
- 重复三次及以上，就该提取
- 相似的逻辑可以用参数化统一
- Cocos 的预制体系统就是 DRY 的体现

## KISS — 保持简单

> *"简单是终极的复杂。能用简单的方式解决，绝不用复杂的方式。"*

```typescript
// ❌ 坏的：过度复杂
function calculateDamage(attacker: Node, defender: Node): number {
  const attackerComponent = attacker.getComponent(Character);
  const defenderComponent = defender.getComponent(Character);

  if (!attackerComponent || !defenderComponent) {
    const error = new Error('Invalid character');
    error.stack = new Error().stack;
    throw error;
  }

  const baseDamage = attackerComponent.attack;
  const defense = defenderComponent.defense;
  const multiplier = attackerComponent.level * 0.1;
  const random = Math.random() * 0.2 - 0.1;
  const finalDamage = (baseDamage - defense) * (1 + multiplier) * (1 + random);

  return Math.max(1, Math.floor(finalDamage));
}

// ✅ 好的：简洁清晰
function calculateDamage(attacker: Character, defender: Character): number {
  const baseDamage = attacker.attack - defender.defense;
  const levelBonus = attacker.level * 0.1;
  const randomFactor = 1 + (Math.random() * 0.2 - 0.1);

  return Math.max(1, Math.floor(baseDamage * (1 + levelBonus) * randomFactor));
}
```

**要点：**
- 代码应该一目了然
- 避免不必要的抽象
- 函数不超过 20 行（理想情况）
- 嵌套不超过 3 层

## YAGNI — 你不会需要它

> *"不要为未来的需求设计代码。未来的需求可能永远不会来，但你现在就要为它们付出复杂度的代价。"*

```typescript
// ❌ 坏的：过度设计
class Hero {
  // 为了"将来可能需要"的多语言支持
  private translations: Record<string, Record<string, string>> = {};

  // 为了"将来可能需要"的多人游戏
  private syncToServer(): void {}

  // 为了"将来可能需要"的存档系统
  private serialize(): string {
    return JSON.stringify(this);
  }

  // 实际当前只需要的功能
  public attack(): void {
    console.log('Attack!');
  }
}

// ✅ 好的：只做现在需要的
class Hero {
  public attack(): void {
    console.log('Attack!');
  }
}
```

**要点：**
- 只为当前明确的需求设计
- 未来需要时再扩展（那时你可能有更清晰的理解）
- 过度设计会扼杀灵活性

## 关注点分离

> *"让每个模块都专注于自己的职责，不要让 UI 逻辑混入业务逻辑，不要让业务逻辑混入数据访问。"*

```typescript
// ❌ 坏的：职责混杂
class Hero extends Component {
  @property(Sprite)
  public avatar: Sprite = null!;

  public attack(): void {
    // 业务逻辑
    const damage = this.calculateDamage();

    // UI 逻辑混入其中
    this.avatar.node.setScale(1.2);
    this.node.setPosition(this.node.position.x + 10, this.node.position.y);

    // 数据访问也混入
    saveToLocal('hero_hp', this.hp);
  }
}

// ✅ 好的：职责清晰
class Hero extends Component {
  private view: HeroView;
  private data: HeroData;

  public attack(): void {
    const damage = this.calculateDamage();
    this.view.onAttack(damage);      // UI 逻辑交给 View
    this.data.recordAttack(damage);  // 数据逻辑交给 Data
  }
}
```

**三层架构：**

| 层级 | 职责 | 示例 |
|------|------|------|
| **View（视图层）** | 显示、动画、用户交互 | HeroView、BattleUIView |
| **Logic（逻辑层）** | 业务规则、状态管理 | Hero、BattleManager |
| **Data（数据层）** | 数据存取、网络请求 | UserData、NetworkManager |

**要点：**
- UI 组件只负责显示和交互
- 业务逻辑不应该知道 UI 的存在
- 数据层与业务层分离

## Cocos Creator 特别心法

### 组件化

每个组件只做一件事，做好一件事：

```typescript
// ✅ 好的：职责单一的组件
@ccclass('HeroMovement')
export class HeroMovement extends Component {
  @property
  public speed: number = 100;

  public move(direction: Vec3): void {
    // 只负责移动
  }
}

@ccclass('HeroAttack')
export class HeroAttack extends Component {
  public attack(): void {
    // 只负责攻击
  }
}
```

### 数据驱动

配置与逻辑分离：

```typescript
// ✅ 好的：数据在外部配置
interface HeroConfig {
  name: string;
  hp: number;
  attack: number;
}

class Hero extends Component {
  public loadConfig(config: HeroConfig): void {
    this.name = config.name;
    this.hp = config.hp;
    this.attack = config.attack;
  }
}

// 配置可以在 JSON、编辑器中管理
const heroConfig: HeroConfig = {
  name: '小柯',
  hp: 100,
  attack: 20,
};
```

### 事件驱动

模块间通过事件通信，保持松耦合：

```typescript
// ✅ 好的：使用事件总线
class EventBus {
  public on(event: string, handler: Function): void {}
  public emit(event: string, ...args: any[]): void {}
}

// 使用
eventBus.on('hero:death', () => {
  // 处理英雄死亡

eventBus.emit('hero:death');
```

## 依赖注入

> *"接口与实现必须隔离。我们使用 Service Locator 模式，配合统一的初始化入口，让模块依赖关系清晰可控。"*

### 核心原则

| 原则 | 说明 |
|------|------|
| **接口与实现隔离** | 所有服务依赖抽象接口，不依赖具体实现 |
| **拒绝装饰器注入** | 避免模块关系破碎，保持代码范式的纯粹性 |
| **统一初始化入口** | 在 GameBootstrap 中按顺序注册所有服务 |
| **构造函数禁解析** | 禁止在构造函数中解析依赖（依赖可能尚未注册） |

### Service Locator 容器

```typescript
// ========== 定义服务接口 ==========

interface IEventManager {
  on(event: string, handler: Function): void;
  emit(event: string, ...args: any[]): void;
  off(event: string, handler: Function): void;
}

interface IAssetManager {
  load(path: string): Promise<any>;
  release(path: string): void;
}

interface IUIService {
  open(uiName: string): Promise<void>;
  close(uiName: string): void;
}

// ========== 定义 Service Token 常量 ==========

const ServiceTokens = {
  EventManager: 'IEventManager',
  AssetManager: 'IAssetManager',
  UIService: 'IUIService',
} as const;

// ========== ServiceLocator 容器 ==========

class ServiceLocator {
  private static services: Map<string, any> = new Map();

  // 注册服务
  public static register(token: string, implementation: any): void {
    if (this.services.has(token)) {
      console.warn(`Service ${token} already registered, will be overwritten.`);
    }
    this.services.set(token, implementation);
  }

  // 解析服务
  public static resolve<T>(token: string): T {
    const service = this.services.get(token);
    if (!service) {
      throw new Error(`Service not found: ${token}`);
    }
    return service as T;
  }

  // 检查服务是否已注册
  public static isRegistered(token: string): boolean {
    return this.services.has(token);
  }
}

// ========== 统一初始化入口 ==========

class GameBootstrap {
  public static init(): void {
    // 按顺序注册所有服务
    // 注意：注册顺序很重要，被依赖的服务先注册！

    // 1. 基础服务
    ServiceLocator.register(ServiceTokens.EventManager, new EventManager());

    // 2. 依赖 EventManager 的服务
    ServiceLocator.register(ServiceTokens.AssetManager, new AssetManager());

    // 3. 依赖前两者的服务
    ServiceLocator.register(ServiceTokens.UIService, new UIService());

    // ... 更多服务
  }
}
```

### 使用方式

```typescript
// ✅ 好的：在生命周期方法中解析依赖
class Hero extends Component {
  private eventManager: IEventManager;
  private uiService: IUIService;

  protected onLoad(): void {
    // 在 onLoad 时解析依赖，此时所有服务已注册
    this.eventManager = ServiceLocator.resolve<IEventManager>(ServiceTokens.EventManager);
    this.uiService = ServiceLocator.resolve<IUIService>(ServiceTokens.UIService);

    // 使用服务
    this.eventManager.on('hero:attack', this.onAttack.bind(this));
  }

  private onAttack(): void {
    this.uiService.open('AttackEffect');
  }

  protected onDestroy(): void {
    // 清理事件监听
    this.eventManager.off('hero:attack', this.onAttack.bind(this));
  }
}

// ❌ 坏的：在构造函数中解析依赖（硬性禁止！）
class Hero extends Component {
  private eventManager: IEventManager;

  constructor() {
    super();
    // ❌ 禁止！此时 GameBootstrap.init() 可能还没调用
    this.eventManager = ServiceLocator.resolve<IEventManager>(ServiceTokens.EventManager);
  }
}
```

### 服务注册顺序

服务注册的顺序非常重要：**被依赖的服务必须先注册**！

```typescript
class GameBootstrap {
  public static init(): void {
    // ✅ 好的：正确的顺序
    ServiceLocator.register(ServiceTokens.EventManager, new EventManager());
    ServiceLocator.register(ServiceTokens.UIService, new UIService()); // UIService 内部可能依赖 EventManager

    // ❌ 坏的：错误的顺序
    ServiceLocator.register(ServiceTokens.UIService, new UIService()); // UIService 初始化时 EventManager 还没注册！
    ServiceLocator.register(ServiceTokens.EventManager, new EventManager());
  }
}
```

### 心法总结

| 要点 | 说明 |
|------|------|
| **使用接口** | 所有服务定义接口，依赖接口而非实现 |
| **Token 常量** | 使用常量避免字符串拼写错误 |
| **生命周期解析** | 在 onLoad/start 中解析，不在构造函数中 |
| **顺序注册** | 按依赖顺序注册服务 |
| **统一入口** | 所有注册在 GameBootstrap.init() 中完成 |

## 心法冲突时如何抉择

设计原则之间可能会冲突，这时需要权衡：

| 场景 | 优先原则 |
|------|----------|
| 简单 vs DRY | 先简单，重复出现再抽取 |
| 灵活 vs YAGNI | 先满足当前需求，保持可扩展性 |
| 性能 vs 可读性 | 瓶颈处优化，其他处可读性优先 |
