# 风之道·架构心法

> *"武学之道，不在于招式繁复，而在于心法通透。心法者，以简驭繁之术也。"*
> —— 吟游诗人 小柯

> 本心法是冒险团框架设计的指导思想，所有架构决策应以此为依归。

---

## 核心心法

> *"最好的架构是刚刚好满足需求的架构，不多一分，不少一毫。"*

1. **简洁胜于复杂** — 简单的代码更容易理解、维护和扩展
2. **变化是永恒的** — 代码必须易于适应变化
3. **重复是敌人** — 每一处知识都应该有单一、明确的表示
4. **不过度设计** — 只为当下需求设计，不为未来猜测
5. **各司其职** — 每个模块都应该有清晰的职责边界，逻辑完整严密
6. **接口先行** — 接口与实现隔离，实现依赖接口，接口不依赖实现
7. **清楚安全边界** — 明确资源生命周期，杜绝内存泄露

## 架构三大支柱

### 1. 职责清晰，逻辑严密

> *"每个伙伴都有自己专一的技能，做好一件事，胜过做平庸的一万件事。"*

**单一职责原则（SRP）扩展：**
- 一个伙伴只做一件事
- 逻辑严密，无遗漏边界情况
- 方法名即文档，无需额外解释

```typescript
// ✅ 好的：职责单一，逻辑严密
class EventManager implements IEventManager {
  private events: Map<string, Set<Function>> = new Map();

  on(event: string, handler: Function): void {
    if (!this.events.has(event)) {
      this.events.set(event, new Set());
    }
    this.events.get(event)!.add(handler);
  }

  off(event: string, handler: Function): void {
    const handlers = this.events.get(event);
    if (handlers) {
      handlers.delete(handler);
      if (handlers.size === 0) {
        this.events.delete(event);
      }
    }
  }

  emit(event: string, ...args: unknown[]): void {
    const handlers = this.events.get(event);
    if (handlers) {
      handlers.forEach((handler) => handler(...args));
    }
  }
}
```

### 2. 接口先行，依赖倒置

> *"契约先行，实现后置。接口不依赖实现，实现依赖接口。"*

**核心原则：**
- 接口定义在 `contracts/` 目录
- 实现放在 `crew/` 目录
- 伙伴永远通过接口交互
- 依赖在 `OnLink()` 时注入

```typescript
// contracts/event-manager.ts
interface IEventManager {
  on(event: string, handler: Function): void;
  emit(event: string, ...args: unknown[]): void;
  off(event: string, handler: Function): void;
}

// crew/event-manager.ts
class EventManager implements IEventManager {
  on(event: string, handler: Function): void { /* 实现 */ }
  emit(event: string, ...args: unknown[]): void { /* 实现 */ }
  off(event: string, handler: Function): void { /* 实现 */ }
}

// 使用时依赖接口
class BattleManager implements ICrew {
  private eventManager!: IEventManager; // 依赖接口，不依赖实现

  async OnLink(eventManager: IEventManager): Promise<void> {
    this.eventManager = eventManager;
  }
}
```

### 3. 清楚安全边界，杜绝内存泄露

> *"来时清清白白，走时干干净净。伙伴的生死由你掌控。"*

**资源管理三原则：**
1. **谁创建谁释放** — 创建资源者负责销毁
2. **配对原则** — 每次 `on` 都有对应的 `off`
3. **生命周期明确** — `OnLink` 建立，`OnUnlink` 清理

```typescript
class BattleManager implements ICrew {
  private handlers: Array<() => void> = [];

  async OnLink(eventManager: IEventManager): Promise<void> {
    // 建立连接
    const onBattleEnd = () => this.handleBattleEnd();
    eventManager.on('battle-end', onBattleEnd);

    // 记录清理函数
    this.handlers.push(() => eventManager.off('battle-end', onBattleEnd));
  }

  OnUnlink(): void {
    // 清理所有连接
    this.handlers.forEach(cleanup => cleanup());
    this.handlers.length = 0;
  }
}
```

## SOLID 原则

> *"面向对象设计的五大基石，掌握它们，你的代码将如诗般优雅。"*

### S — 单一职责原则 (Single Responsibility Principle)

**一个类或模块应该只有一个引起它变化的原因。**

```typescript
// ✅ 好的：职责分离
class Hero {
  // 只负责英雄的属性和行为
  public hp: number = 100;
  public attack(): void {}
}

class HeroView {
  // 只负责英雄的显示
  public updateSprite(hero: Hero): void {}
}

class HeroData {
  // 只负责英雄数据的存取
  public save(hero: Hero): void {}
}

// ❌ 坏的：职责混杂
class Hero {
  public hp: number = 100;
  public attack(): void {}
  public updateSprite(): void {}  // 视图职责
  public saveToDatabase(): void {} // 数据职责
}
```

**要点：**
- 一个类只做一件事
- 如果你想不出一个简洁的类名，说明它做了太多事
- Cocos Creator 中的组件天然符合单一职责

---

### O — 开闭原则 (Open-Closed Principle)

**软件实体应该对扩展开放，对修改关闭。**

```typescript
// ✅ 好的：通过策略模式扩展
interface AttackStrategy {
  attack(target: Node): void;
}

class MeleeAttack implements AttackStrategy {
  attack(target: Node): void {
    console.log('近战攻击');
  }
}

class RangedAttack implements AttackStrategy {
  attack(target: Node): void {
    console.log('远程攻击');
  }
}

class Hero {
  private attackStrategy: AttackStrategy;

  public setAttackStrategy(strategy: AttackStrategy): void {
    this.attackStrategy = strategy;
  }

  public attack(): void {
    this.attackStrategy.attack(this.node);
  }
}

// ❌ 坏的：每次添加新攻击方式都要修改 Hero 类
class Hero {
  public attack(type: string): void {
    if (type === 'melee') {
      // 近战逻辑
    } else if (type === 'ranged') {
      // 远程逻辑
    }
    // 添加新类型需要修改这里
  }
}
```

**要点：**
- 通过接口和抽象类隔离变化
- 使用策略模式、模板方法模式
- Cocos 的组件系统本身就是开闭原则的体现

---

### L — 里氏替换原则 (Liskov Substitution Principle)

**子类应该能够替换父类而不破坏程序的正确性。**

```typescript
// ✅ 好的：子类完全遵循父类契约
abstract class Enemy {
  abstract attack(): void;
}

class Goblin extends Enemy {
  attack(): void {
    console.log('哥布林攻击');
  }
}

// 任何使用 Enemy 的地方都可以用 Goblin 替换
function makeEnemyAttack(enemy: Enemy): void {
  enemy.attack(); // 无论是 Goblin 还是其他 Enemy 都能正常工作
}

// ❌ 坏的：子类破坏了父类的契约
class DummyEnemy extends Enemy {
  attack(): void {
    // 什么都不做，破坏了父类的预期行为
  }
}
```

**要点：**
- 子类不能削弱父类的方法功能
- 子类不能抛出父类没有预期的异常
- Cocos 组件继承时要注意保持行为一致性

---

### I — 接口隔离原则 (Interface Segregation Principle)

**客户端不应该依赖它不需要的接口。**

```typescript
// ✅ 好的：接口细粒度分离
interface Movable {
  move(x: number, y: number): void;
}

interface Attackable {
  attack(): void;
}

interface Healable {
  heal(value: number): void;
}

// 只实现需要的功能
class Wall implements Movable {
  move(x: number, y: number): void {}
}

class Hero implements Movable, Attackable, Healable {
  move(x: number, y: number): void {}
  attack(): void {}
  heal(value: number): void {}
}

// ❌ 坏的：臃肿的接口
interface GameEntity {
  move(x: number, y: number): void;
  attack(): void;
  heal(value: number): void;
  fly(): void;
  swim(): void;
}

// 墙不需要攻击和治愈，但被迫实现这些方法
class Wall implements GameEntity {
  move() {}
  attack() {} // 空实现
  heal() {}  // 空实现
  fly() {}   // 空实现
  swim() {}  // 空实现
}
```

**要点：**
- 接口应该小而专注
- 不要强迫类实现不需要的方法
- TypeScript 的类型系统让接口隔离更容易实现

---

### D — 依赖倒置原则 (Dependency Inversion Principle)

**高层模块不应该依赖低层模块，两者都应该依赖抽象。**

```typescript
// ✅ 好的：依赖抽象
interface ILogger {
  log(message: string): void;
}

class ConsoleLogger implements ILogger {
  log(message: string): void {
    console.log(message);
  }
}

class GameService {
  private logger: ILogger;

  constructor(logger: ILogger) {
    this.logger = logger;
  }

  public doSomething(): void {
    this.logger.log('Something happened');
  }
}

// ❌ 坏的：依赖具体实现
class GameService {
  private logger: ConsoleLogger; // 依赖具体类

  constructor() {
    this.logger = new ConsoleLogger();
  }
}
```

**要点：**
- 依赖接口而非实现
- Cocos 的 `@property` 装饰器本质上就是依赖注入

## DRY — 不要重复自己

> *"每一处知识都应该有单一、明确的表示。如果你发现自己在复制粘贴，那就是设计问题的信号。"*

```typescript
// ❌ 坏的：重复的代码
function getHeroHP(hero: Node): number {
  const component = hero.getComponent(Hero);
  return component ? component.hp : 0;
}

function getEnemyHP(enemy: Node): number {
  const component = enemy.getComponent(Enemy);
  return component ? component.hp : 0;
}

// ✅ 好的：提取通用逻辑
function getComponentHP<T extends { hp: number }>(
  node: Node,
  componentClass: Constructor<T>,
): number {
  const component = node.getComponent(componentClass);
  return component ? component.hp : 0;
}

// 使用
const heroHP = getComponentHP(heroNode, Hero);
const enemyHP = getComponentHP(enemyNode, Enemy);
```

**要点：**
- 重复三次及以上，就该提取
- 相似的逻辑可以用参数化统一
- Cocos 的预制体系统就是 DRY 的体现

## KISS — 保持简单

> *"简单是终极的复杂。能用简单的方式解决，绝不用复杂的方式。"*

```typescript
// ❌ 坏的：过度复杂
function calculateDamage(attacker: Node, defender: Node): number {
  const attackerComponent = attacker.getComponent(Character);
  const defenderComponent = defender.getComponent(Character);

  if (!attackerComponent || !defenderComponent) {
    const error = new Error('Invalid character');
    error.stack = new Error().stack;
    throw error;
  }

  const baseDamage = attackerComponent.attack;
  const defense = defenderComponent.defense;
  const multiplier = attackerComponent.level * 0.1;
  const random = Math.random() * 0.2 - 0.1;
  const finalDamage = (baseDamage - defense) * (1 + multiplier) * (1 + random);

  return Math.max(1, Math.floor(finalDamage));
}

// ✅ 好的：简洁清晰
function calculateDamage(attacker: Character, defender: Character): number {
  const baseDamage = attacker.attack - defender.defense;
  const levelBonus = attacker.level * 0.1;
  const randomFactor = 1 + (Math.random() * 0.2 - 0.1);

  return Math.max(1, Math.floor(baseDamage * (1 + levelBonus) * randomFactor));
}
```

**要点：**
- 代码应该一目了然
- 避免不必要的抽象
- 函数不超过 20 行（理想情况）
- 嵌套不超过 3 层

## YAGNI — 你不会需要它

> *"不要为未来的需求设计代码。未来的需求可能永远不会来，但你现在就要为它们付出复杂度的代价。"*

```typescript
// ❌ 坏的：过度设计
class Hero {
  // 为了"将来可能需要"的多语言支持
  private translations: Record<string, Record<string, string>> = {};

  // 为了"将来可能需要"的多人游戏
  private syncToServer(): void {}

  // 为了"将来可能需要"的存档系统
  private serialize(): string {
    return JSON.stringify(this);
  }

  // 实际当前只需要的功能
  public attack(): void {
    console.log('Attack!');
  }
}

// ✅ 好的：只做现在需要的
class Hero {
  public attack(): void {
    console.log('Attack!');
  }
}
```

**要点：**
- 只为当前明确的需求设计
- 未来需要时再扩展（那时你可能有更清晰的理解）
- 过度设计会扼杀灵活性

## 关注点分离

> *"让每个模块都专注于自己的职责，不要让 UI 逻辑混入业务逻辑，不要让业务逻辑混入数据访问。"*

```typescript
// ❌ 坏的：职责混杂
class Hero extends Component {
  @property(Sprite)
  public avatar: Sprite = null!;

  public attack(): void {
    // 业务逻辑
    const damage = this.calculateDamage();

    // UI 逻辑混入其中
    this.avatar.node.setScale(1.2);
    this.node.setPosition(this.node.position.x + 10, this.node.position.y);

    // 数据访问也混入
    saveToLocal('hero_hp', this.hp);
  }
}

// ✅ 好的：职责清晰
class Hero extends Component {
  private view: HeroView;
  private data: HeroData;

  public attack(): void {
    const damage = this.calculateDamage();
    this.view.onAttack(damage);      // UI 逻辑交给 View
    this.data.recordAttack(damage);  // 数据逻辑交给 Data
  }
}
```

**三层架构：**

| 层级 | 职责 | 示例 |
|------|------|------|
| **View（视图层）** | 显示、动画、用户交互 | HeroView、BattleUIView |
| **Logic（逻辑层）** | 业务规则、状态管理 | Hero、BattleManager |
| **Data（数据层）** | 数据存取、网络请求 | UserData、NetworkManager |

**要点：**
- UI 组件只负责显示和交互
- 业务逻辑不应该知道 UI 的存在
- 数据层与业务层分离

@ccclass('HeroMovement')
export class HeroMovement extends Component {

interface HeroConfig {

class Hero extends Component {

## 伙伴系统设计

> *"伙伴即服务，冒险团即容器。羁绊、编队、召唤、分别，乃伙伴之生命周期。"*

### 核心概念

| 概念 | 代码 | 说明 |
|------|------|------|
| 冒险团 | Squad | 服务容器，管理所有伙伴 |
| 伙伴 | Crew | 服务实例 |
| 契约 | Contract | 接口定义（contracts/） |
| 花名册 | Roster | 伙伴名称常量（registry/） |
| 建立羁绊 | Bind | 创建实例，登记花名册 |
| 编入队伍 | Link | 激活伙伴，注入依赖 |
| 召唤伙伴 | Summon | 运行时获取伙伴 |
| 与伙伴分别 | Unlink | 销毁伙伴，清理资源 |

### 伙伴生命周期

```
   Bind                Link              Summon              Unlink
建立羁绊 ───────────> 编入队伍 ──────────> 召唤伙伴 ──────────> 与伙伴分别
   ↓                   ↓                   ↓                   ↓
构造函数            onBind()            OnLink()             技能方法()
   ↓                   ↓                   ↓                   ↓
创建实例            初始化准备           激活伙伴             使用技能         OnUnlink()
不可用              不可用              可用                运行时           销毁清理
```

### 伙伴契约

```typescript
// contracts/crew.ts - 伙伴基础契约
interface ICrew {
  onBind?(): void;                        // 建立羁绊后调用，同步
  OnLink?(...deps: unknown[]): Promise<void>; // 编入队伍时调用，异步
  OnUnlink?(): void;                      // 与伙伴分别时调用，同步
}
```

### 契约示例

```typescript
// contracts/event-manager.ts
interface IEventManager {
  on(event: string, handler: Function): void;
  emit(event: string, ...args: unknown[]): void;
  off(event: string, handler: Function): void;
}
```

### 伙伴实现

```typescript
// crew/event-manager.ts
class EventManager implements ICrew, IEventManager {
  private events: Map<string, Set<Function>> = new Map();

  onBind(): void {
    // 初始化数据结构
    Journal.Info('EventManager 建立羁绊');
  }

  async OnLink(journal: Journal): Promise<void> {
    // 接收依赖
    this.journal = journal;
    Journal.Info('EventManager 编入队伍');
  }

  on(event: string, handler: Function): void { /* 实现 */ }
  emit(event: string, ...args: unknown[]): void { /* 实现 */ }
  off(event: string, handler: Function): void { /* 实现 */ }

  OnUnlink(): void {
    // 清理资源
    this.events.clear();
    Journal.Info('EventManager 与伙伴分别');
  }
}
```

### 花名册

```typescript
// registry/roster.ts
export const ROSTER = {
  EVENT_MANAGER: 'IEventManager',
  ASSET_MANAGER: 'IAssetManager',
  UI_SERVICE: 'IUIService',

```

### 统一召集

```typescript
// embark.ts
export function embark(): void {
  // 1. 建立羁绊
  const eventManager = Squad.Bind(ROSTER.EVENT_MANAGER, EventManager);

  // 2. 编入队伍
  Squad.Link(ROSTER.EVENT_MANAGER, journal);

  // 运行时
  const eventManager = Squad.Summon<IEventManager>(ROSTER.EVENT_MANAGER);
  eventManager.emit('test');

  // 游戏结束
  // 3. 与伙伴分别
  Squad.Unlink(ROSTER.EVENT_MANAGER);
}
```

### 心法总结

| 要点 | 说明 |
|------|------|
| **接口先行** | 契约定义在 contracts/，实现放在 crew/ |
| **依赖倒置** | 伙伴依赖接口，不依赖实现 |
| **生命周期清晰** | Bind → Link → Summon → Unlink |
| **资源安全** | OnLink 建立，OnUnlink 清理 |
| **统一召集** | 所有伙伴在 embark() 中统一管理 |

## 心法冲突时如何抉择

设计原则之间可能会冲突，这时需要权衡：

| 场景 | 优先原则 |
|------|----------|
| 简单 vs DRY | 先简单，重复出现再抽取 |
| 灵活 vs YAGNI | 先满足当前需求，保持可扩展性 |
| 性能 vs 可读性 | 瓶颈处优化，其他处可读性优先 |
